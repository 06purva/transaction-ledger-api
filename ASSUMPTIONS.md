# Assumptions

This document describes the assumptions and implementation decisions made for the Transaction Ledger API where the assessment did not specify exact behavior.

## 1. Account Creation

- Every account is assigned a unique UUID generated by the system.
- The account name is required and must satisfy the API's validation rules.
- Every new account starts with a balance of `0.00`.
- The account creation timestamp is generated by the database; clients cannot set the initial balance or creation timestamp.

## 2. Transaction Amounts and Types

- Transaction amounts must be greater than zero.
- Amounts are represented as decimal values with a maximum of two decimal places to support standard currency precision.
- Supported transaction types are `CREDIT` and `DEBIT`.
- A credit increases the account balance, while a debit decreases it.
- A debit is rejected if the account has insufficient funds.
- Account balances cannot become negative or exceed the maximum value supported by the database schema.

## 3. Transaction References and Duplicates

- Each transaction must include a reference ID.
- A reference ID must be unique within an account, rather than globally across all accounts.
- Reusing a reference ID for the same account is treated as a duplicate and must not create another transaction or change the balance.
- The same reference ID may be used for different accounts, subject to the applicable transfer rules.

## 4. Transaction History

- Transaction history is retrieved for a specific existing account.
- The API supports filtering by transaction type. If no type is specified, both credit and debit transactions are returned.
- Pagination uses `page` and `limit` parameters.
- Transactions are returned in newest-first order. The transaction ID is used as a secondary sort key when timestamps match.
- The response includes pagination metadata, including the current page, page size, total record count, and total number of pages.

## 5. Data Integrity and Atomicity

- Transactions are immutable after creation. Database-level protection prevents updates and deletions of ledger records.
- Account balance changes and their corresponding ledger entries are performed within a database transaction.
- If an operation fails, its balance changes and ledger entries must be rolled back together.
- Database constraints are used to enforce applicable integrity rules, including unique transaction references per account and positive transaction amounts.

## 6. Money Transfers

- Transfers are supported as an additional feature beyond the core assessment requirements.
- Both the source and destination accounts must exist and must be different accounts.
- The source account must have sufficient funds.
- A successful transfer creates a debit entry for the source account and a credit entry for the destination account.
- Both balance changes and both ledger entries are committed atomically. If any part fails, the entire transfer is rolled back.
- Account locks are acquired in a consistent order to reduce the risk of deadlocks during concurrent transfers.

## 7. Validation and Error Handling

- Account IDs must be valid UUIDs.
- Invalid request data is rejected with an appropriate client error.
- Missing accounts, duplicate references, insufficient funds, and other expected conflicts are reported with appropriate HTTP status codes and meaningful error messages.
- Optional transaction descriptions may be omitted; when provided, they must satisfy the API's validation rules.

## 8. Scope

- The application uses PostgreSQL for persistent storage and Prisma ORM for database access.
- The API is designed to run locally using the configuration and setup instructions in the README.
- Authentication, authorization, and multi-currency support are outside the scope of the supplied assessment unless separately required.
